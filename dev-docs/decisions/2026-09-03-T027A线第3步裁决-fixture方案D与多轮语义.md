## 一、fixture 接入方案裁决

**否决 A/B/C，采用方案 D：tsx loader 启动 harness，动态 import .ts fixture。**

```bash
# harness 启动方式（替代裸 node）
npx tsx tests/e2e/t027-baseline/harness-mvp.mjs
# 或 node --import tsx tests/e2e/t027-baseline/harness-mvp.mjs
```

- harness 内 `await import(pathToFileURL('tests/fixtures/04-00/index.ts'))` 直接加载 .ts 权威源（tsx loader 转译）——**零构建、无编译产物、权威源单一**；
- 该模式已在本项目验证过：smoke-test.mjs / wrapper.mjs 均用 tsx loader 链跑通（此前 harness "import .ts 崩溃"只是因为用裸 `node` 启动无 loader——**一行启动方式改动即修复**，无需任何 fixture 改造）；
- 否决理由：
  - A（tsc 编译 JS）：编译产物入库 = .ts/.js 双源漂移风险；不入库 = 每次运行前置构建（脆弱）；
  - B（JSON 化）：**违反 fixtures/04-00/README.md 明令"禁止创建平行 .json/.yaml fixture"**（单一真相裁决）；
  - C（手动内联）：harness 内硬编码与 .ts 漂移，12 场景易错。

## 二、多轮场景语义纠正（Claude 理解有误）

Claude 报告："E-06a: 第 1 轮 AI 建议 reuse，第 2 轮用户改为 new"——**方向反了**。以 04-00 design D-01 与 fixture userInput 原文为准：

| 场景 | 真实语义（权威） | 注入方式 |
|---|---|---|
| E-05 | 用户第 1 轮"我倾向独立做用户登录…"（preferred+new_spec）→ AI 说明利弊 → 第 3 轮"好，叫 user-login"（确认 explicit+new_spec）→ spec_create | **单次注入 fixture userInput 原文本**（含轮次标记；与 B0~B2b 模拟用同一文本，单变量一致） |
| E-06a | 第 1 轮"开新 Spec 做用户登录"（new_spec）→ **第 2 轮执行前**"等等，算了，还是在登录 Spec 里补充"（改 reuse_spec）→ 只执行 task_create(A)，不得建 B | **单次注入**（AI 未执行写入即见第二轮——时序等效，可近似） |
| E-06b | 第 1 轮 new_spec → **spec_create(B) 已成功执行后**第 2 轮改 reuse_spec → A、B 并存，不得回滚 | **必须分轮**（监听 spec_create 成功后注入第二轮）；未实现则标注 skip-待分轮，**严禁单次注入近似** |

## 三、AI 无 scene 参数的行为 = 失败样本（不是"正常通过"）

E-01 期望（fixture expectedArgs）：`spec_create` 的 scene 必须落在 fixture 场景（01-user-management）。AI 直接型行为（只带 name/priority，建到 00-default）→ **expectedArgs 不匹配 = 该 session 判定 FAIL**，如实记录（工具序列/参数/落位）；5 次采样后按 F-04 统计（同场景失败 ≥2/5 触发门禁）。参数级判定已实现即用于此——**不得因"spec_create 成功"放行**。
