## 一、亲验事实链

| 层 | 状态 |
|---|---|
| LrnevToolPayload 接口（canonical） | ✅ 只有 `errors?: LrnevErrorInfo[]`（L73）——**无 error 单数** |
| adapter L72 | ❌ `error: errors.length===1 ? errors[0] : undefined`——**通过索引签名 `[key: string]: unknown` 静默塞入**（TS 不报错但接口未声明） |
| createToolOutputSchema | ❌ 加了 `error: ErrorInfoSchema.optional()`——声明了一个 canonical 接口不存在的字段 |
| 测试 14/14 | ✅ 通过（schema optional + 测试构造 error）——**自洽循环，掩盖真实问题** |

## 二、为什么这是错误的（三条）

1. **接口 vs 实现的漂移**：adapter 写 error，接口没有——靠索引签名兜底，**TS 类型系统已失效**（未来任何代码读 payload.error 都不会被类型检查）
2. **双真相回归**：error 与 errors[0] 并存——违反 03-00"一个规范化 payload 只能有一个构建来源"
3. **测试自洽循环**：schema 允许 error → 测试构造 error → 通过。但 canonical 是 errors——**测试验证的是错误的结构，不是真实协议**

## 三、正确修复（P0-2 真方案）

**根因**：DataSchema 缺实际返回字段（如 SpecFrontmatter 的 updated）→ -32602。

```
1. 回退 adapter L72 的 error 行（恢复只写 errors）
2. 回退 createToolOutputSchema 的 error 字段
3. 保留 49f0941 中 DataSchema 字段补齐（updated 等）——这是正确的部分
4. 测试保持读 errors[0]（ba82d1b 已改）
5. 验证：-32602 消失（DataSchema 补齐后），测试读 errors[0] 通过
```

**判定标准**：canonical payload 的每个字段都必须在 LrnevToolPayload 接口声明（无索引签名兜底依赖）；schema 必须与接口一致。
