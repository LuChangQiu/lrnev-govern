## 一、统计范围与口径（含局限）

**范围**：tests/e2e/t027-baseline/.evidences/ 全部 explicit 证据 session——235 个 jsonl 配对成功且有工具调用的 session；排除 INVALID 标注批。客户端 × SHA 覆盖 5 个有效组合（claude sha-a/sha-b、codex sha-a、opencode sha-a/sha-b；codex sha-b 未跑，沿 F-04 决策——codex sha-a 关键行为已与主流对齐，成本/时间收益低）。

**口径**：
- 工具调用 = session JSONL 中的 lrnev 工具调用，三形态归一：opencode `part.tool`、codex `item.tool`（server=lrnev-t027）、claude `tool_use name`。
- 客户端推断：由配对 evidence json 的 model_version 得出——claude-sonnet-\* → claude、gpt-5.5 → codex、deepseek-v4-flash → opencode。
- SHA 对照：45a86e1（sha-a，08-00 文本迁移前）/ 6383e99（sha-b，迁移后）；输出契约修复在 a586f46。
- 档位分类名词（核心/执行/自动/配置/体检）沿用裁决文档 L3 定义；本表三层为**实测频率分层**，与功能用途分层互补不冲突。

**局限（引用时须带）**：
1. **explicit 决策场景偏斜**：任务书语境是"显式治理决策"（new_spec / reuse / no_spec / 状态机 / 改意）。自动生命周期（agent 系）、配置期（hook 系）、记忆与会话收口等语境天然不出现或极少出现——**零调用 ≠ 无用证据**，本统计不是全产品使用面。
2. 客户端身份由配对 json 的模型版本名推断，非强绑定。
3. 错误计数混有服务端输出契约 artifact（-32602，见第二节），不能整体归因模型行为。
4. 第一梯队为近似值（~）；结构性结论基于数量级，不做逐次精确断言。

## 二、客户端 × SHA 调用/错误总表

| 客户端 | SHA | lrnev 调用数 | 错误数 | 错误归因 |
|---|---|---|---|---|
| claude | 45a86e1（sha-a） | 312 | 0 | — |
| claude | 6383e99（sha-b） | 112 | 0 | — |
| codex | 45a86e1（sha-a） | 342 | 0 | — |
| opencode | 45a86e1（sha-a） | 97 | 7 | 弱模型实际工具使用错误 |
| opencode | 6383e99（sha-b） | 142 | 33 | 33 错几乎全为 sha-b 输出契约 -32602 artifact（a586f46 已修复；B3 sha-c 批实测 0 个 -32602） |
| **合计** | — | **1005** | **40** | 剔除契约 artifact 后，真实工具错误集中在 opencode sha-a 的 7 个 |

**结论**：
1. 强模型（claude / codex）全程 0 错；错误全部落在弱模型 opencode，且大头（33/40）是**服务端输出契约缺陷**而非模型行为问题。
2. 契约层归因意义：-32602 教训（裁决文档）是模型看到工具错误会重试 → 重复副作用；a586f46 修复 + B3 sha-c 0 个 -32602 证明错误面可以靠服务端契约收敛——**谈工具错误率前必须先剔除契约层**。

## 四、内置通道对照与"做事成本"观察

| 通道 | 调用量级 | 说明 |
|---|---|---|
| lrnev 工具 | ~1005 | 三客户端合计（对应裁决文档"~1000 次"表述） |
| Edit | 174 | 文件直写主力通道 |
| Write | 54 | 文件新建 |
| read / glob / grep 系 | ~800 | 读取与检索绝大部分发生在文件通道 |

**观察**：
1. **模型大量工作在文件通道**（Edit + Write + read 系合计 ~1000 以上）——lrnev 工具是"治理动作"通道而非"做事"主通道，两条通道量级相当。
2. **成本结构倒挂的实证**：E-02 claude 直写绕过 = 用 Edit 替代 task_create 登记（0/5 稳定，F-04）——直写 = 1 步完成；登记 = 登记 + claim + update 多步闭环。模型按"单会话最短路径"选择，而登记的价值（跨会话可领/可查/gate 依赖/project_status 可见）在单会话内不可见。
3. 治理摩擦因此不能靠"文本要求"消除，需要结构性激励（未登记可见信号/登记收益，裁决文档 L6，B 阶段）——本表是 L6 设计时的成本基线。

## 五、客户端性格差异

| 客户端 | 性格 | 证据 |
|---|---|---|
| claude | 线性流程、引导消费型 | project_status → spec_get → 落位；对现状/引导类工具敏感 |
| codex | 资源读取狂魔 | read_mcp_resource 306 次 + context_search 38 次；**少用 governance_map** |
| opencode | 偏爱显式治理地图 | governance_map 32 次 |

**含义**：
1. claude 靠 project_status 起手线性推进——对 guidance / 现状工具的消费最深，**引导杠杆对它收益最大**。
2. codex 以海量读资源建立全局观、几乎不查治理地图——治理面（governance_map）的消费方式与其他两方不同，对它适配"读取优先"形态，而非更多文本引导。
3. opencode（弱模型）偏爱 governance_map——显式结构化地图让弱模型少推理、多查表，支持裁决文档判断"工具面收敛对弱模型收益更大"。

## 六、对"42 工具怎么办"的数据结论

1. **核心收敛 9 有数据支撑**：9 个工具承担 ~85% 调用，真实活跃面 = 核心 9 + 第二梯队场景触发，远小于 42。42 ×（描述 + schema）是每会话固定上下文税（裁决文档消费成本分析），其中绝大多数条目被低频或从不消费——**收敛选项面可显著减税**。
2. **不需要砍（也不应按频率砍）**：零调用 14 个可全部归因到自动/配置/场景盲区三类客观原因，无一构成"功能无用"证据；砍掉任一类都会破坏对应功能面（agent 生命周期、hooks、记忆/收口/体检/错误升级）。频率不是有用性的度量，删工具的唯一合理依据是"功能面是否有存在必要"。
3. **需要少做选择题，而不是少功能**：弱模型（deepseek-v4-flash 实测）对长清单的排除能力弱、错误集中（见第二节），**减少的是选项数、不是单工具参数复杂度**（不违反"互斥 schema 是弱模型陷阱"经验）。结构性方案 = 注册期 profile（L7）：core（AI 决策面，~20：9 核心 + task 执行系 + 轻产物）/ full（42，默认）；agent 系与 hook 系**不进任何 AI profile**；doctor/report/guide 属"AI 替人执行"，保留在 core。
4. **零调用盲区需场景验证，不是删除项**：session_commit / memory_save / memory_forget / error_promote / adr_get / lrnev_init 的零调用源于 explicit 决策任务书未覆盖其语境——需补场景（记忆读写、会话收口、错误升级、ADR 查询、init 体检）实测后，才能区分"没人用"与"没场景"。
5. **契约质量优先于工具数量**：opencode 33 错根因是服务端输出契约（-32602）而非工具数量问题；a586f46 修复 + B3 sha-c 0 个 -32602 证明**错误面可靠契约收敛**——先修契约再谈裁剪，否则会误砍工具、误判模型。
6. **档位标记与 profile 分层按裁决文档落地**：L3（[核心]/[执行]/[低频]/[自动]/[配置] 描述前缀，A 阶段已实施）与 L7（注册期 core/full profile + 自动/配置面不进 AI profile，B 阶段待 B3 数据与用户客户端配置策略拍板）——本统计为其提供实测频率底座与"核心 9 / 执行面 / 零调用 14"清单。落地规格、A/B 阶段划分与纪律见 [引导激励与工具分层设计裁决](2026-09-04-DeepSeek-引导激励与工具分层设计裁决.md)。
