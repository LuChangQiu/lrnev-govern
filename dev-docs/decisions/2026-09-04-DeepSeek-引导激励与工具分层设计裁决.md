# 引导激励与工具分层设计裁决（DeepSeek 审查方，用户授权推进）

- **日期**: 2026-09-04
- **作者**: DeepSeek（审查方）
- **状态**: 设计定稿；分两阶段落地（A 阶段 = 不依赖 B3 数据的低风险项，立即实施；B 阶段 = 依赖 B3/后续数据裁决项）
- **背景**: 用户讨论"做事成本结构（spec 三文档/锚点/claim）""hooks sync+abort""42 工具"后授权：按审查方设计推进，要求站在 AI 层与 User 层全面思考

## 一、实测证据（T-027 双 SHA × 三客户端，~120 sessions）

1. E-02 claude 0/5 稳定：直写编辑（Edit 路径）不调 task_create 登记；codex 自认只读；opencode 走 task_create_many 达成（sha-a 5/5）。
2. E-06a/b claude 两 SHA 同现"自动归档刚建 B"（6/10 + 5/10）——AI 撤销直觉 vs design"不自动回滚"。
3. 工具调用分布（235 sessions）：9 个核心工具承担 ~85% 调用；agent_* 自动触发（codex register 12 次）；hook_* 5 个、session_commit/memory_forget/error_promote/adr_get/lrnev_init 零调用（场景未覆盖 + 配置期/自动类）。
4. 客户端性格差异：claude 线性（project_status→spec_get→落位）；codex 资源读取狂魔（read_mcp_resource 306 次）；opencode 偏爱 governance_map。
5. 内置文件通道调用 ~800 次（Edit 174/Write 54/read 系）vs lrnev 工具 ~1000 次——模型大量工作在文件通道。
6. -32602 事件教训：模型看到工具错误会重复重试 → 重复 ADR/任务副本（报错≠写入失败，AI 无法区分）。

## 二、AI 层分析（模型如何决策、如何消费）

**决策模型**：AI 在单会话内选择"最短路径达成用户请求且看起来正确"的动作。由此推导三个缺口：

1. **认知缺口**（引导缺位）：不知道 task 登记/不归档的存在价值——G1-G4 修复中（B3 验证）。
2. **激励缺口**（路径成本倒挂）：直写编辑 = 1 步完成；task_create 登记 = 登记 + claim + update 闭环多步。登记的价值（跨会话可领/可查/gate 依赖/project_status 可见）在**单会话内不可见** → 模型理性选择直写。文本引导只能部分修正（告诉它"应该"），结构性修正需要让"登记"产生单会话内可感知的收益或"不登记"产生可见成本。
3. **直觉缺口**（撤销/清理直觉 vs 终态语义）：AI 把"归档刚建的 B"当作负责任的清理；不知道 archived 是状态机终态（E-08：archived 拒绝 spec_update）且归档影响跨会话可审计性。同理：工具报错后 AI 重试直觉（-32602 教训）——"报错可能=写入已成功"这类服务端语义模型无法从错误码推断。

**消费成本**：42 工具 × (描述 + schema) 是每会话固定上下文税；实测活跃面 ~20（9 核心 + 场景触发），agent_*/hook_* 等对 AI 是纯噪音。弱模型（deepseek-v4-flash 实测）对长清单的排除能力弱于强模型——工具面收敛对弱模型收益更大。

## 三、User 层分析（人的治理意图、信任、成本匹配）

1. **治理意图**：spec/task/ADR 结构的存在理由是**跨会话/多 agent 可交接、可审计、可 gate**。这些价值全部在单会话时间尺度之外——这是激励错位的根源，也是"AI 直觉"与"结构"冲突的根源。
2. **成本匹配**：用户明确认可"简单需求不开 spec、开了就要守结构"。推论：**结构承诺一旦做出（spec 存在、任务在列），AI 的行为应与结构一致**；结构之外（无 spec 的简单改动）AI 自由度高是特性不是缺陷。所以治理杠杆应聚焦"已承诺结构内的行为一致性"，而不是扩大强制面。
3. **信任与可见性**：AI 直写绕过/自动归档时，人通常不知情（除非 diff/report）。doctor/lrnev_report 是人的体检通道，但实测 AI 极少主动调（report 3 次/235 sessions）——人依赖 AI 报告健康度时，AI 不主动体检 = 可见性缺口。分层不能砍掉"AI 替人执行"的工具（doctor/report/guide），否则人失去间接通道。
4. **hooks sync+abort 的 User 语义**：人配 abort = "这件事不成功就不该继续"。但 -32602 教训显示 abort 时写入已发生、模型会重试 → 重复副作用。User 层结论：abort 只建议用于幂等/前置校验型 hook；文档必须写明"abort 不回滚已写入"。

## 五、A 阶段实施规格

### G5：E-06a/b 归档语义显式化（DECISION_BOUNDARY）
- **WORKFLOW_OVERVIEW 全局句**（guidance.ts）："归档边界：archived 是状态机终态。AI 不替用户自动归档/删除 Spec——用户改主意不构成自动归档依据，是否归档由用户明确决定（spec_update）。刚创建的 Spec 同理，不得自我回退。"（实测 WORKFLOW_OVERVIEW 是最高频消费 guidance 面，E-06a/b 的 AI 在动作前必读）
- **spec_update 工具描述**（guidance.ts TOOL_DESCRIPTIONS.spec_update）追加决策边界句：archived 终态 + 不替用户做归档决定 + 仅用户明确要求时执行。
- **spec_create 成功响应不植入无条件【决策边界】行**（实施中验证的协议约束）：DECISION_BOUNDARY 是 direction 不一致提示的专用语义（05-00 裁决 Q4），spec_create 恒有行会破坏 Profile 协议锁定（guidance=[FACT, RECOMMENDATION]）并使模型对边界标记脱敏。SPEC_CREATION_SUCCESS_FOLLOWUP 语义锚扩展为文档锚。
- 理由：design 语义（不自动回滚）一直存在但从未在 AI 动作点显式化；E-06a/b 实测证明 AI 需要在动作发生前读到它。

## 七、L7 细化：三类消费方分层（用户 2026-09-04 讨论记录，待议）

**洞察**：42 不是"频率问题"而是"消费方混装问题"。42 个工具服务的对象根本不同：
- **AI 决策面**（~30 个）：scene/spec/task/context 系——每会话真用的就 9 个核心；
- **自动化面**（agent_register/heartbeat/unregister/list）：codex 会话自动 register 12 次（实测），AI 根本不该"选择"它；
- **运维/人面**（doctor/report/hook_*、lrnev_init）：配置期与体检期用，部分由"AI 替人执行"（doctor/report——实测 AI 极少主动调，report 3 次/235 sessions，属可见性缺口，不能简单砍掉）。

**方案（比"标档位让模型排除"更结构）**：按消费方分组，注册期裁剪——MCP server 启动参数/配置 `--profile`：
- `core`（AI 决策面）：~20 个（9 核心 + task 执行系 + 轻产物）——日常执行 AI 用；
- `full`（默认，42）：治理型 AI / 人机混合；
- 自动化面（agent 系）与运维面（hook 系）**不进任何 AI profile**（agent 系由连接层自动调，hook 系由人配置）——但注意：doctor/report/guide 是"AI 替人执行"工具，应留在 core 或按用户偏好可配。

**约束与风险**：
- 不违反"互斥 schema 是弱模型陷阱"经验（减少的是选项数，不是单工具参数复杂度）；
- 裁剪发生在注册期，不碰业务 core/渲染器（复用 19 组注册函数，风险低）；
- 需要用户定客户端配置策略（claude mcp 配置按项目/按客户端）；弱模型（deepseek-v4-flash）受益最大；
- 与 L3 档位标记互补：L3 是"标了让模型自己排除"（零成本先行），L7 是"注册期就不给"（结构性根治）；
- **落地前置**：B3 数据 + 用户对客户端配置策略拍板；代码形态 = tools/index.ts 注册函数按组标注 + server 启动参数过滤。

## 八、L6/L7/B4 最终裁决（2026-09-04 晚，用户授权 DeepSeek 定案）

### 裁决 1（L6 结构性激励）：三步走，不幻想强制单会话登记
B3 实证：G1 引导送达但 claude E-02 仍 0/5 直写（激励缺口）；E-06a vs E-06b 分化（AI 尊重"用户明确要求的已建成物"、撤销"自己抢跑的产物"）；lrnev 拦不住文件通道 Edit（模型直写发生在 lrnev 工具调用之外）。
1. **G1 措辞歧义消除**（立即实施）：现引导"仅修改既有正文内容 → 可直接编辑原文件"给了"补充=改文档"的合法归类。修订：开发请求（加/实现/补充功能）→ task_create 登记后再实施；直接编辑仅限需求细化/文档维护，不能替代开发任务登记。B4 用同 fixture 复测（fixture 不动，保历史可比）。
2. **E-02 0/5 记录为"单会话全能 agent 直写基线"**：产品上无法也不应强制单会话登记（登记价值在跨会话/多 agent/交接）；门禁判定维持（意图达成标准不变），不作为发布阻塞，作为观测资产与多 agent 场景验证的对照基线。
3. **lrnev_report 未登记改动债务检测**（User 层可见性）：spec 文档改动 vs 任务活动的 mtime 级提示（warnings）——给人看（AI 看了无效已被实证）；放 B 阶段（发布后迭代），需防误报设计。
4. 若 B4（G1 修订后）E-02 仍 0/5 → 场景语义演进（E-02 加"交接/多 agent"语境变体）作为 04-00 后续任务走治理登记。

### 裁决 2（L7 消费方分层）：实现 --profile core|full，默认 full 向后兼容
- **core = full − 9 个"AI 不该主动选"**：agent_register/agent_heartbeat/agent_unregister/agent_list（自动面，连接层自动调）+ lrnev_hook_list/trigger/tail_log/enable/disable（配置面，人配置用）。core ≈ 33 个。
- task/adr/error/memory/session_commit/doctor/report/guide 全留 core（AI 可能需要；doctor/report 是"AI 替人执行"不能砍——User 层可见性通道）。
- 实现：tools/index.ts 注册函数按组标注 profile 面 + server 启动参数 `--profile core|full`（默认 full）；注册期裁剪不碰业务 core/渲染器；与"互斥 schema"经验不冲突（减选项不减参数复杂度）；弱模型（opencode/deepseek-v4-flash）受益最大。
- 客户端配置策略：claude/codex mcp 配置的 args 加 `--profile core`（用户按客户端选）；文档说明 core/full 差异。进本次发布。

### 裁决 3（G5 验证 / B4）：B4 与发布前验证合并
- G5（d9dfb9a）不在 sha-c；E-06a 1/5（归档仍现）是 G5 的验证对象。
- **B4 = 发布内容全部合入后冻结新快照（sha-d）**：含 G1 修订 + G5 + L7 + 统一审查收尾 → 真机复测矩阵：claude E-02/E-06a/E-06b ×5 + opencode E-02 ×5（≈$5，$50 闸内）。
