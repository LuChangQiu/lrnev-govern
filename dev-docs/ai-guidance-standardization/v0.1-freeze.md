### 2.1 Five Semantic Text Roles (Boundary #1)

| Role | Prefix | Responsibility | Enforcement | Defined In |
|------|--------|----------------|-------------|------------|
| FACT | 【事实】 | lrnev / workspace evidence | None (informational) | §3, Table row 1 |
| RECOMMENDATION | 【建议】 | lrnev heuristics | None (advisory, can be overridden) | §3, Table row 2 |
| DECISION_BOUNDARY | 【决策边界】 | Client/user confirmation | Client boundary (not server constraint) | §3, Table row 3 |
| EXECUTION_CONSTRAINT | 【执行约束】 | Server deterministic code | Server enforced (blocks on violation) | §3, Table row 4 |
| ACTION_HINT | 【下一步】 | lrnev / client | None (optional next step) | §3, Table row 5 |

**Key Principles**:
- RECOMMENDATION does not block actions
- DECISION_BOUNDARY does not create server constraints
- EXECUTION_CONSTRAINT MUST correspond to deterministic code validation

### 2.2 Three-Dimensional Analysis Framework (Boundary #2)

**Purpose**: Analysis framework for design review and case validation. **NOT** a universal protocol requiring all messages to carry these fields.

| Dimension | Typical Values | Usage |
|-----------|----------------|-------|
| `provenance` | workspace, lrnev, client_asserted, user_quote | Determines information source |
| `role` | fact, recommendation, decision_boundary, execution_constraint, action_hint | Determines semantic responsibility |
| `enforcement` | none, client_boundary, server_enforced | Determines enforcement mechanism |

**Explicitly Forbidden**:
- ❌ Using single numeric `priority` to compare different semantics
- ❌ Requiring all MCP responses to include provenance/role/enforcement fields
- ❌ Treating GoalAssessor output as `user_quote` or `client_asserted`

## 6. Explicitly Excluded from v0.1

The following are **NOT INCLUDED** in v0.1 and cannot be claimed as implemented:

### 6.1 NOT INCLUDED: Automatic Decision Persistence

- ❌ No `user_intent` field in tool schemas
- ❌ No `messages` history in governance state
- ❌ No Decision Record directory or database
- ❌ Server does not persist guesses about user direction

**Rationale**: Per spec §5.1, USER_DECISION can only come from user_quote or client_asserted. Server has no mechanism to capture or persist these from client context.

### 6.2 NOT INCLUDED: Universal Three-Dimensional Schema

- ❌ No requirement for every MCP response to include provenance/role/enforcement
- ❌ No structured `{ provenance, role, enforcement, content }` protocol
- ❌ Framework is analysis-only, not runtime protocol

**Rationale**: Per spec §4 and F-02, three dimensions are for design review, not message serialization.

### 6.3 NOT INCLUDED: Numeric Priority System

- ❌ No `priority: number` field to rank semantics
- ❌ No algorithmic comparison like "CONSTRAINT > USER_DECISION > RECOMMENDATION"
- ❌ Conflicts resolved by evaluating dimensions separately, not numeric order

**Rationale**: Per spec §4, "不得使用单一数字 priority 比较不同语义" — semantic conflicts require contextual judgment, not numeric sorting.

## 7. Version Evolution Rules

### 7.1 When v0.2 is Required

A new version (v0.2, v0.3, etc.) is **REQUIRED** when:

1. **Role definition changes**: Adding new roles, changing enforcement semantics, or redefining responsibility
2. **Framework expansion**: Adding new dimensions beyond provenance/role/enforcement
3. **Constraint inventory breaking change**: Removing a real constraint (e.g., state machine change)
4. **Case semantics change**: Altering the meaning of E-01 through E-05 behaviors

### 7.2 When Version Update is NOT Required

The following changes can be made **within v0.1**:

1. **Adding constraints**: New real constraints can be added to inventory without version bump (additive change)
2. **Fixing typos**: Correcting spelling or grammar in specification text
3. **Clarifying examples**: Adding more positive/negative examples to §3 table
4. **Cross-reference updates**: Updating file paths or line numbers in §11 audit evidence

### 7.3 Runtime Constants and Documentation

**Rule**: Runtime constants, MCP tool instructions, and test assertions **MUST** reference this specification rather than creating independent definitions.

**Examples**:
- ✅ GOOD: `// See semantic-authority-model.md §3 for role definitions`
- ❌ BAD: Hardcoding role definitions in tool code that diverge from spec
- ✅ GOOD: Test fixture references `inventorySection: '§1.1'`
- ❌ BAD: Test creates its own constraint list without spec reference
