## 主线：把「交税」变成「分红」

lrnev 的根本处境：用户前期交流程税（写 requirements、过 gate、建 task），但结构化数据的红利只兑现了一小部分（接手快照、追溯靠人翻）。

**发展主线一句话：让攒下的结构化数据持续产出回报。回报越大，用户越愿意交税，入口依从性问题反而自己缓解一半。**

每一步都在回答「用户为什么继续用」，而不是「还能加什么功能」。

**3.0.0 印证（2026-09-07）**：scene 04 的 B 系列真机对照给了主线一个残酷而干净的注脚——同一「建议新建、用户明确复用、应落位登记」场景（E-02），opencode 从 4/5 走到 5/5（输出契约修复后行为首次无污染），claude 四个 SHA 连续 0/5：引导句 5/5 送达确认、认知缺口与措辞歧义均已修，模型仍直写。「**交税在单会话内看不见分红**」时，文本引导再强也拦不住直写——既是主线的反证式印证，也是第二步执法环的立项证据（观测：`dev-docs/ai-guidance-standardization/deliverables/04-00-final-observation-report.md`「B3/B4 补充观测」节）。

## 两个生死问题（比任何功能都优先）

### 问题一：维护态缺口（决定留存）

项目越成熟，工作越是小增量（给已完成特性加参数、修边角），lrnev 的流程却越不贴身。这不是边角问题——**小增量是大多数真实工作的形态**。缺口不补，用户会在度过初建期后慢慢绕开。

**为什么现有轻产物（memory/errorbook/ADR）接不住**：它们是**知识轨道**（记「这件事教会了我们什么」），不是**工作轨道**（记「这件事做没做完、对应哪个需求」）。典型场景「给已完成的登录功能加个记住我选项」：errorbook 没踩坑、memory 不是约定、ADR 没有决策、新开 spec 写不出独立验收——AI 真机表现为乱开新 spec（2026-06-05 xpaas-gen-v3 观察）。

**定性修正（2026-06-12，GPT 交叉评审 + 核对 `docs/GOVERNANCE-FLOW.md` 后）：不是「没家可放」，是「有家但 AI 找不到门」。**

协议层的维护通道**已经存在**：状态机明文允许 `completed -> in-progress` 回退；GOVERNANCE-FLOW.md 原话「只是增量加需求时，在本版 task_create 即可，不必新开 spec」，且「需求落位」一节已把 context_search 落位定义为 AI 的判断职责。真实缺口是**发现性**：

1. 这条路写在 `docs/GOVERNANCE-FLOW.md` 里，AI 会话中不会读它；
2. 决策时刻 AI 面前的分流指引（CLAUDE.md 规则、工具 followup）是二元的——「开 spec 还是直接做」，没有第三分支「落位到现有 spec」；
3. 「先 context_search 落位再动手」没有任何工具层提醒在那个时刻把它顶到 AI 面前。

**方向（v1 = 铺显已有路径，不发明新实体、不加 flag）**：纯 followup/steering 工程——`spec_create` 的 followup 加「先 context_search 确认是否该落位到现有 spec」；给 completed spec 加 task 时自动提示状态回退语义（`completed -> in-progress`）。`--maintenance` flag、`change_record` 新实体都属于轻度过度设计，**真机验证「路显性了 AI 还是不走」之后才考虑动 API**。scene 01 实施过程本身会产出维护态标本（completed spec 的后续小修补），是 v1 设计的第一手需求素材。

**关键设计约束：必须比「直接改代码」只多一步操作，否则没人用。**

**3.0.0 处置状态（2026-09-07 评审）：发现性缺口已闭环；问题升格为激励缺口——部分解决，残余归第二步。**
- 三条发现性缺口已铺显闭环：`spec_create` followup 现含「context_search 找到对应 Spec 用 task_create 落位」指引（`src/core/SpecManager.ts`）；completed spec 上加 task 提示 `spec_update` 合法回退 in-progress（`src/core/TaskManager.ts`）；四路分流（含第三分支「落位到现有 spec」）统一在 followup / guide 工作流 / 常驻模板三层（v2.1 起，`src/mcp/guidance.ts`、`docs/AI-ADAPTATION.md`；v2.3 发布审计把 guide 与 server instructions 同步到同口径）。
- 3.0.0 再进一步：把关键边界句下沉到**动作点的工具描述**（G5——`spec_update` 描述含【决策边界】「archived 终态、用户改主意不构成自动归档依据」；对照 G1 修的是 `spec_get` 过程点建议句）。B4 真机验证「动作点绑定 > 过程点建议」：G5 生效 E-06a 归档率 4/5→0/5，round2 全转征询/保留；G1 建议句对 claude E-02 无效（四 SHA 0/5）。
- 残余 = **激励缺口**（B4 定案）：claude E-02 四 SHA 0/5 = 认知缺口已修、措辞歧义已消后的纯激励/路径问题（登记路径在该会话内比直写多步且无即时回报）；L6 结构性激励设计待用户拍板，裁决 1.4 把 E-02 场景语义演进（加交接/多 agent 语境变体）登记为 04-00 后续任务——不阻塞 3.0.0 发布。
- 「真机验证后再动 API」裁决已被部分回答：路显性了 claude 仍不走 → 维持原结论，不给维护通道加 API（`--maintenance`/`change_record` 在源码与文档中均不存在），按顺序推进第二步执法环。「只多一步」约束仍是验收标尺。

### 问题二：入口依从性（决定价值下限）

硬校验只能拦「已经进了流程的坏数据」，拦不住「AI 压根不开 spec 直接改代码」。当前最外层入口靠 CLAUDE.md 式规则——提示词载体有三个结构性缺陷：

1. **注意力衰减**：会话越长权重越稀释（I-19 已观察到 AI 对常驻 warning 脱敏，同一机制作用于入口规则）。
2. **执行时机错位**：规则在会话开头注入，但需要在「准备改代码的那一刻」被想起。
3. **lrnev 是被动方**：MCP server 只能看见发给它的调用；AI 完全不调它时，连 warning 的机会都没有。

**解法：执法点搬到动作发生的地方，三道环（按通用性排序，见下节修正）**：

| 环 | 载体 | 时机 | 通用性 |
|---|---|---|---|
| git 卡点 | pre-commit 配方：diff 动了源码但无 task 活动 → 提醒（默认）/拒绝（严格模式可选） | 提交时 | ✅ 100% 客户端无关、模型无关 |
| 事后审计 | doctor/report 加项：对比近期 git 提交与 task 状态变更，列出「未治理的变更」 | 任意时刻 | ✅ 住在 lrnev 体内 |
| harness 钩子 | SessionStart 注入治理快照、PostToolUse 查 in_progress task 并注入提醒 | 实时 | ✗ 按客户端，做薄垫片 |

**git 环的安装悖论（2026-06-12 实现者评审指出，落地前必须定策略）**：pre-commit hook 要先装进用户仓库才生效——安装动作本身就是一个入口依从性问题，且是全链路侵入性最高的一步（动用户 git 配置）。但注意它与 AI 依从性问题有本质差别：**hook 安装是人类的一次性动作，AI 依从是每会话的持续行为**——前者恰好落在「主动选择的绕过」框架里（装不装是一次知情决定），难度低一个量级。落地策略倾向：**`lrnev integrate git` 显式命令安装（与 integrate <client> 同一模式），init 绝不自动装、只在 followup 提一句**；配方需探测既有 hook 管理器（husky / core.hooksPath）并链式追加而非覆盖，不与用户已有钩子打架。

**顺序硬依赖（不可交换）**：doctor「未治理变更」审计命中的恰恰大多是维护态小改动。若审计环先上、维护通道还没铺显，审计会对无处安放的变更持续报警，用户没有合理的消警方式，只能学会无视——这正是 I-19 的脱敏机制，等于亲手把最硬的执法环训练成噪音。**维护通道（问题一）是审计环的前置依赖，不是平行任务。**

**残余缺口及其正当性**：三道环全上，用户一句「别管 lrnev 直接改」仍能绕过——这个缺口**不该堵**，「只引导不强制」对人类同样适用。关键区分：

> 绕过有两种：**遗忘导致的绕过**（AI 忘了/没看见/脱敏）和**主动选择的绕过**（用户明确说不要）。目标是把前者降到零，把后者保留为权利。提示词两种都防不住；三道环消灭前者、放行后者。做到这一步，入口问题就算闭环——不是 100% 依从率意义上的，而是「所有偏离都是知情选择」意义上的。

**3.0.0 处置状态（2026-09-07 评审）：仍存在——三道环的实现一行未动，仍是 3.0.0 之后第一战略优先级。**
- 实现核查：`src/` 无 git 集成代码（git 只出现在忽略路径、工作区向上查找注释与证据契约 sha 字段）、CLI 无 `integrate` 子命令、`init` 不生成 AGENTS.md、doctor 检查家族（目录/哨兵/坏引用/stale/registry/hook 健康等）无「未治理变更」审计——三道环全空。
- 3.0.0 给本题补了三块正面输入：① **动作点引导实证**（B4：G5 绑进动作点工具描述有效、过程点建议对 claude 无效）——「执行时机错位」的最廉价解法已在工具描述层部分兑现，harness 实时环不再是唯一手段；② **claude 0/5 vs opencode 5/5 同场景分野** = 「软提醒有效性模型相关」的官方复现（呼应定位判断），弱模型先受益于确定性下两层（输出契约修复即 4/5→5/5）；③ **decision_context 客户端声明通道（3.0.0）**——用户决定第一次成为协议内可声明信号（`source: client_asserted`、strength explicit/preferred/unspecified、direction、只影响本次调用、不落盘不阻断），是「主动选择的绕过是权利」的协议化雏形；注意它靠客户端自愿声明，不解决遗忘型绕过，与执法环互补而非替代。
- 顺序硬依赖维持且前置已满足：维护通道铺显（v2.1）+ 动作点引导（3.0.0）都在场，审计环上马不会对「无处安放的变更」空报警；report/doctor 宿主已在（v2.2/v2.0），「未治理变更」审计 = 既有 doctor 检查家族加一项，不动 report/doctor 边界。

## 通用性原则（2026-06-12 修正，覆盖此前「per-client 接入包」提法）

目标受众不限于 Claude/GPT，还包括 DeepSeek、Qwen 等任意模型。关键概念区分：**差异在客户端（harness），不在模型**——模型不直接连 lrnev，总是跑在某个 harness 里。所以问题是「每个客户端」而非「每个模型」，且已解掉一大半：

**「通用插件标准」已经存在，就是 MCP 本身。**lrnev 做成 MCP server 等于已押中唯一的通用插件协议——工具能力层零适配成本即通用。真正不通用的只有实时钩子一层。三个杠杆：

1. **执法主力放最通用的层**：git pre-commit + doctor 审计是脊梁（100% 通用），harness 钩子降级为可选增强。**通用执法的脊梁是 git，不是 harness。**
2. **提示层用 AGENTS.md**：行业正在收敛的跨客户端指令标准（Codex/Cursor/Zed 等共认）。`lrnev init` 生成一份 AGENTS.md 治理段落，替代分别维护 CLAUDE.md / .cursorrules / 各家格式。
3. **harness 钩子做成薄垫片（LSP 架构思路：一个服务端，N 个薄客户端）**：lrnev CLI 提供为钩子设计的命令（如 `lrnev hook session-start` 输出治理快照、`lrnev hook pre-edit` 查 in_progress task），**所有判断逻辑写一次、住在 lrnev 体内**；各客户端「适配」只是 10 来行配置，可用 `lrnev integrate <client>` 自动生成，社区可贡献模板。垫片坏了只损失增强体验，git 层照常兜底——退化是优雅的。

| 层 | 载体 | 通用性 | 优先级 |
|---|---|---|---|
| 工具能力 | MCP | ✅ 全通用 | 已完成 |
| 提交卡点 | git pre-commit + doctor 审计 | ✅ 全通用 | **第一** |
| 指令注入 | AGENTS.md | ◐ 大部分客户端 | 第二（init 时生成） |
| 实时钩子 | 各 harness hooks | ✗ 按客户端 | 薄垫片 + `lrnev integrate`，锦上添花 |

**3.0.0 追更（2026-09-07）**：上表的执行面没有变，但三行有了新事实——
- 「工具能力（MCP）」行完成度升级：3.0.0 双通道契约（structuredContent canonical 信封 + outputSchema 声明 + 逐工具渲染文本）把 MCP 层从「能力存在」做到「契约稳定」——机器消费方有了可编程的稳定数据面（text 通道破坏性变更一次即固化，README §4）。「已完成」从此含契约含义，不只是工具存在。
- 「指令注入」行的实际形态 = 常驻模板**单源化**（`docs/AI-ADAPTATION.md` 为唯一权威源，用户按客户端贴进 CLAUDE.md / AGENTS.md / Cursor rules）；`lrnev init` 自动生成 AGENTS.md 仍未做（归第二步）。
- 「实时钩子」行：钩子**运行时**已加固（3.0.0 ADR-0003 hook drain——触发先写 invoked、进程退出统一 drain ≤5s、超时补写 timed_out；`lrnev_hook_tail_log` 成排查钩子的唯一手段；doctor 健康统计剔除 invoked 脚手架记录），叠加 v2.0 起的 CLI/MCP 对等与 hook 全生命周期可经 MCP 管理——**薄垫片的地基（判断逻辑在体内、钩子日志可查）已经齐了**，差的只是 `lrnev integrate` 配置生成与各家 harness 适配本身。
- 「提交卡点（git 环）」仍是全表唯一空白行 = 第二步本体。

附注：模型越弱（指令遵循越差），确定性的下两层贡献越大——与多模型受众目标同向（3.0.0 B3/B4 已实证：契约修复让 opencode E-02 4/5→5/5，claude 文本引导四 SHA 无效）。另外 harness 钩子只能跑 shell 命令、调不了 MCP 工具，**CLI/MCP 对等（scene 01 的 S1）正是钩子环的地基**，不只是工程洁癖。

4. ☐ **第四步（受众扩张，可缓）：国际化 alias 表 + 工具瘦身。**中文模板硬契约（I-13）挡住非中文用户/模型；42 个 MCP 工具（v2.3 现状）的 schema 对弱模型和小上下文客户端是负担（可按场景分组暴露或合并低频工具）。前三步验证产品有人要之后再做。——**已部分落地（2026-09-07 标注）**：工具瘦身以 `--profile core|full` 分层先行（2026-09-04 裁决 L7，3.0.0 交付——`core` 33 = `full` 42 − `agent_*` 自动面 4 + `lrnev_hook_*` 配置面 5 共 9 个"AI 不该主动选"工具，弱模型客户端受益；默认 `full` 向后兼容）；国际化 alias 表仍维持"可缓"。（2026-09-07 再追更：3.0.0 同窗口落地了响应面的「无用即删」纪律——T-006 裁决回退 guidance 结构化挂载与 `reported_user_quote` 输入字段（380 录制件 0 命中、零消费即删），与工具瘦身同源：schema 与字段也是模型/脚本的税，不消费就不该收。）

## 明确不做的（守住边界）

- **不做 agent 编排/子任务调度**——那是 harness 的地盘，进去就是和 Claude Code/Codex 正面竞争，必输。
- **不做语义检索/向量**——零模型是身份，不是省钱。
- **不追新客户端的每个新特性**——薄垫片做最主流的两三家，其余靠 git 层兜底 + 社区模板。

**3.0.0 无越界确认（2026-09-07）**：42 工具全量注册无新增面（`--profile` 只是裁剪，core=33/full=42）；`agent_*` 仍是运行态注册/claim 面，无任何子任务调度/编排逻辑；hooks 仍只跑本地 shell；依赖零新增（无 LLM/Embedding/向量库，`package.json` 依赖与 2.x 同族）。「不做」清单无需修订。

## 定位判断（存档）

- lrnev 当前是 **prosumer 工具**：甜区是「一个人开多 AI 窗口做长期迭代的正经项目」，不是大众市场。受众天花板接受，把产品做深不做宽。（README 3.0.0 重写的「适合/不适合」口径与此一致。）
- 「跨客户端中立」是有意的赌注（非风险）：赌多客户端接力人群随模型差异化增长。（3.0.0 把赌注真机化：B3/B4 用 claude + opencode 双 SHA 对照矩阵验证中立性可交付，实测矩阵成文于 `docs/AI-ADAPTATION.md`。）
- 软提醒（ai_followup）的有效性是模型相关的，硬校验是模型无关的——scene 01 把治理保障从「依赖模型听话」迁移到「协议层强制」，是面向多模型受众最划算的鲁棒性投资。（3.0.0 拿到官方实证：同场景 claude 四 SHA 0/5 vs opencode 5/5——引导送达率 5/5 ≠ 行为改变率；确定性层是唯一不依赖运气的投资方向。）
- 内层硬校验保证「进了流程的数据不烂」，三道环保证「流程本身必然在场」——两层合起来，lrnev 才从「一套需要被想起来的工具」变成「一个绕不开但可以说不的协议」。（3.0.0 新增 decision_context：「主动选择的绕过是权利」第一次有协议表达——客户端声明 source=client_asserted 的 strength/direction，服务端只作参考输入渲染、不落盘不阻断；但声明权在客户端，遗忘型绕过仍归执法环。）

### 3.0.0 之后的产品事实（战略意义）

- **MCP 响应双通道契约（03-00 M1/M2）**：每次调用同返 `structuredContent`（canonical 信封 `response_version:'1'`/ok/data/errors/ai_followup/anchor_context/summary_context）+ `content[0].text`（逐工具渲染的模型可见文本），全工具声明 outputSchema。**战略意义**：结构性重估「分红面」——结构化数据从「AI 读的文本」扩成「程序可编程的数据面」，治理数据第一次有稳定的机器契约（text 通道破坏性变更一次即固化）；「模型读文本、脚本读契约」的双通道正好服务 prosumer 双受众。
- **Guidance 五角色语义体系 + T-006 字段回退（05-00）**：引导收敛为【事实】【建议】【决策边界】【执行约束】【下一步】五角色；但结构化 guidance 挂载字段实测零消费被裁决回退（380 录制件 0 引用，≈24.2% 响应体积纯重复税），纯函数库保留为契约测试面。**战略意义**：「逐字段门禁、无用即删」成为响应面纪律（与第四步工具瘦身同源）；五角色文本通道 = 「只引导不强制」语义的工程化（约束与建议从此可被模型区分，决策边界显式化）。
- **decision_context 客户端声明通道（05-00 T-002/T-003）**：四个落位工具接受 `source: client_asserted` 决策上下文，条件规则由真实链路负向校验。**战略意义**：用户决定（含 no_spec「不落位」）成为协议内可声明信号——「主动选择的绕过是权利」的协议化雏形（见问题二处置）；也兑现 scene 01 09-00 spec「user_decision 来源悖论」的重写方向：服务端不伪造用户意图，只接收客户端声明。
- **F-04 截断元数据（ADR-0001）与 hook drain（ADR-0003）**：截断从布尔升级为 text_status 三态 + query_meta；async hook 触发先写 invoked、退出 drain ≤5s、超时补写 timed_out。**战略意义**：两条「收口窗口 P0 悬空账」把可靠性钉在模型可见层——AI 拿到的每段上下文都标注「预算截断 / 源残缺」不把噪声当正文；钩子从裸 fire-and-forget 变成可诊断（`lrnev_hook_tail_log` 唯一排查手段）——**执法环（git/harness）若上马，日志与可见性是它的前提**，这一层已在 3.0.0 补齐。
- **`--profile core|full` 工具面分层（L7）**：core 33 = full 42 − 9 个「AI 不该主动选」工具。**战略意义**：工具瘦身的第一种形态不是删工具而是**按档位裁剪暴露面**——schema 税按客户端能力收，弱模型/小上下文客户端受益且向后兼容（默认 full）。
- **审定决策档案体系（dev-docs/decisions/，2026-09 文件治理）**：讨论区（ai-discussions）本机留存、审定终稿镜像入库（只增不改、GitHub 可核验）、逐任务过程背书分流归档。**战略意义**：发布声称（CHANGELOG/ADR/报告的数据与判定）从此有可点击的审定依据——「多个 AI 在同一份文件真相上辩论收敛」从一次性实验变成可复制的发布流程（见推广观察追更）。
