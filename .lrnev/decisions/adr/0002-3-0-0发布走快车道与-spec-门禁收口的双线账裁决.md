# 0002. 3.0.0 发布走快车道与 spec 门禁收口的双线账裁决

## 状态

accepted（已执行，2026-09-07 DeepSeek 审查方裁决 + 用户拍板）

## 背景

3.0.0 发布过程中出现"双线账"：**release 快车道**（B4 真机验证 → CHANGELOG → version bump → 文件治理 → 内容终审）推进速度先于 **spec 门禁线**（scene04 specs 01-05 与 scene01 08-00 的任务全部 completed、实现合入、证据入库，但 requirements.md frontmatter 的 status 停在 draft/in-progress——spec 级从未走 spec_gate_check(completion) + spec_update 收口）。深层原因：任务驱动开发中 spec 收口是手动动作（gate 只检查不自动改状态），落库流程只做了 task_update 没做 spec_update——本仓库 dogfooding 自身遗漏了收口（lrnev_report 的 unclosed 体检若跑会报出）。另有 06-00 交付物问题：client-integration-guide / mcp-response-conformance 两份文档内容与 3.0.0 实现大面积不一致（研究期草案），曾被迁入 docs/ 作为正式用户文档，终审判为阻断。

## 决策

1. **release 快车道不阻塞于仪式性收口**：3.0.0 发布先行——T-006 等任务级落库、B4 发布前验证、证据入库全部真实完成，spec 状态 flip 是记录性动作（非实质性工作），不构成发布阻塞。
2. **spec 收口在 push 前补齐**：scene04 01-00~05-00 与 scene01 08-00 按实际状态回填 completed（gate 验证后逐级 spec_update，2026-09-07 R1 执行）。
3. **06-00 交付物退回研究档案**：client-integration-guide / mcp-response-conformance 退回 dev-docs/ai-guidance-standardization/ 并加"研究期草案、与实现不一致"注记；正式客户端文档待真实 MCP 客户端接入后重写（06-00 spec 保持未收口，验收不满足）。
4. **未来规范**：spec 级收口（completion gate + spec_update）应与 release 同步或先于；task_update 把最后任务标 completed 时考虑给收口引导（产品改进候选，动作点引导原则，B 阶段评估）。

## 后果

- 双线账显式记录，不再隐性偏离。
- .lrnev spec 状态在 GitHub push 前与实际一致（避免"任务全 done、spec 标 draft"的仓库级矛盾）。
- 06-00 的"基础文档无条件发布"spec 文本与交付物现状的张力显式化：文档成熟度不足时退回档案，spec 验收不硬凑。
